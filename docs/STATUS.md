Reason: undo compares states on every push, and comparing by identity avoids reading pixels; one mask path keeps the preview and the export identical.

Reason: the window stays responsive, and a daemon thread cannot block closing the app.

On the user's RTX 2050 (4 GB) DirectML runs out of memory with this model at 1024, so in practice it runs on the CPU: about 13 s to load the model and 20 s per image. Reason: the plan asks for the GPU where it works and an automatic fallback.

No runtime behavior changed.
- 2026-09-24: STATUS.md's module map and decision log described a `RETRY_MS` retry timer (100 ms) for a background-removal result arriving mid-drag or mid-stroke; it no longer exists. Plan 06 (the lock/busy-overlay work) replaced it with an outright refusal to start or apply an edit while a removal is locked or a drag/stroke is in progress, so a result never needs to wait and retry. `RETRY_MS` is removed from the module map's list of `app.py` public names. Reason: a code review found the docs describing dead code.
- 2026-09-24: `cancel_removal()` no longer unlocks the image itself; it only sets the stop event and cancels the remover. The unlock (`_end_removal()`) now runs asynchronously, only once the worker thread's `_run_removal` confirms it actually stopped, through a new `cancelled` signal on `_RemovalSignals` (the same pattern `finished`/`failed` already used). `MainWindow._closing` is set as the first line of `closeEvent`, before it cancels, so that confirmation is never emitted once the window may already be destroyed. Reason: a code review found that the old synchronous unlock let a user cancel and immediately start a second run while the first run's worker thread (and its `ProcessRemover`/model-download cleanup) was still winding down, racing two unsynchronized writers onto the same model `.part` file or two threads onto one `multiprocessing.Connection`. Several `tests/test_app.py` cancellation tests asserted the old synchronous unlock directly after calling `cancel_removal()`/`close()`/loading a new image; they now wait for the worker thread (reusing the existing `_finish_removal` join-then-`processEvents` helper) before asserting the unlock, except `test_close_cancels_the_run_and_ends_the_child`, which no longer asserts `is_removing` at all, since closing intentionally suppresses that signal.

## Deviations from plans

- 01-prototype: File > Exit (Ctrl+Q) was added so the File menu isn't empty in milestone 1. It's a standard action with no other effect.
- 03-rotate-flip-paint: the approved plan listed Ctrl+R and Ctrl+Shift+R for the turns, but Ctrl+R is already Reset. The turns use Ctrl+] (right) and Ctrl+[ (left) instead.
- 03-rotate-flip-paint: the plan said the angle box records an undo step on `editingFinished`. It applies on `valueChanged` with keyboard tracking off instead: a typed value still applies once (on Enter or focus loss), and arrow clicks, which never emit `editingFinished`, apply at once as one step each.

## Known issues

- Tests run only on Python 3.14. The declared floor is 3.10; ruff's `target-version = "py310"` guards syntax but not runtime or API differences.
- Without the `bg` extra installed, `tests/test_matting.py` is skipped (it needs numpy), so the gate checks less. The venv here has it installed.
- Closing the app while background removal runs leaves the daemon thread to end with the process; its result is dropped. If Qt has already deleted the window when the thread finishes, emitting the result signal can print a `RuntimeError` to the console. This is harmless.
